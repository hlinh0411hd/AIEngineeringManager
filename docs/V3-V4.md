# V3–V4: implementation and setup

Updated 2026-11-02. This document supersedes the earlier “Phase 3–4 deferred” status. Changes are source-only: no compilation, executable checks, UI launch, local evaluation, inference, export, publishing or update installation was performed for this request. The existing executable remains unchanged until the user runs Build.bat. XML/source inspection is not runtime verification.

## Dashboard and task entry

The WPF shell follows the supplied purple dashboard: sidebar navigation, Task/Autonomous/Away controls, running state, task controls, robot illustration, system counts, current work, recent projects/activity, provider status, Agents, Local AI, Approvals and Updates. Existing project/task/provider/settings controls remain available. The robot is native vector artwork. Layout and visual fidelity have not been checked in a running window.

Dashboard values come from persisted records and active execution. Project progress means reviewed task count, and current progress means completed internal steps. Daily calls are manager invocation reservations, not vendor quota. CPU measures the manager process; RAM uses Windows system metadata. VRAM is Unknown until the explicit NVIDIA metadata action succeeds. Unknown authentication, billing, balances and quota remain Unknown.

Autonomous applies the existing planner to new tasks. Away changes persisted continuation policy. Both preserve budgets, permissions, review gates and checkpoints. Pause waits for the current step; Stop cancels and retains history.

For tools, first save a workflow in Workflows. In the normal Tasks composer, choose it in **Tool workflow** and use **Assign & run**; Run/resume, queue scheduling, stop and final review stay attached to that task. A unique saved workflow name contained in the request can be matched deterministically within the selected project. This is not unrestricted natural-language tool planning: creating a new workflow still requires explicit tool inputs and dependencies. Tool workflows run without an AI planning call.

## Workflow behavior

Persisted workflows have a registered project, 1–50 uniquely named steps, tool IDs, operation IDs, JSON inputs and a dependency DAG. A value such as `{"$from":"video.artifactPath"}` refers to the JSON output of a declared dependency. Arrays and whole-object replacement are intentionally not an arbitrary scripting language.

Each step receives a durable request ID before execution. Writes, model calls and publishing require separate profile permissions and approval tied to exact inputs/configuration. Large inputs and outputs are stored as SHA-256-bound local artifacts. Publishing always requires individual approval. `AutoContinueLocal` can continue reviewed-by-policy internal results, but never approves a publishing request or final workflow completion.

Requests and results requiring review appear in Tools; the task's **Tool requests / artifacts** button opens that queue. Approve the request there, then resume the task. Review generated artifacts and results before marking them complete. A stopped, interrupted or failed write is never silently replayed. Inspect backend state and create a new workflow/request if a retry is appropriate. Dependent steps wait while independent steps may proceed.

Tools and AI share the existing resource-slot/project-root exclusion mechanism. Overlapping registered project/source/workspace roots cannot run concurrently. API polling does not reserve additional AI calls. A tool action marked as using AI reserves one manager invocation before calling the tool; the external tool can perform more than one internal model call, which the manager cannot count exactly.

## Model reliability and usage

Existing Economy/Balanced/Performance routing and historical feedback remain in use. New persisted usage sums include only token fields actually reported by Codex `turn.completed` frames; partial coverage and unknown providers remain explicit. There is no invented currency cost or quota estimate. Truncated or missing CLI usage frames cannot be recovered by this parser.

Ollama qualification remains limited to Classification/Extraction. The optional advanced evaluation button runs four objective local probes for JSON compliance/basic arithmetic, records accuracy, elapsed time and system available-RAM delta, and does not grant coding/planning capability. It is not a broad reasoning, content-quality or coding benchmark. RAM delta is not model VRAM consumption.

Routing temporarily excludes an Ollama model/category after at least three timeout/validation failures in its latest five eligible observations, with a 15-minute window. A newer perfect standard qualification can clear that exclusion. Invalid local task-assignment responses are recorded as validation failures. Manual disabled/model/permission gates remain intact. No model was evaluated during implementation.

## Reviewed local updates

Updates accepts an existing, separately prepared local build folder for the manager or a configured desktop tool. It never downloads, builds or creates an archive automatically. Build.bat explicitly builds the updater and copies its runtime files alongside the desktop build when the user runs it.

Preparation copies a bounded package (10,000 files / 2 GB), excludes data/config/secrets, computes per-file hashes and creates a reviewable manifest. Applying requires reviewing the target and manifest hash while new dispatch is suspended. The helper is copied outside the installation before launch, waits for the parent/target executable to exit, backs up replaced files and applies only listed paths. Reparse points and protected data/workspaces are rejected.

For manager updates, a fresh SQLite online backup is made immediately before approval. The new app must render its disabled startup window and acknowledge a nonce before normal work is unlocked. Startup failure triggers restoration of replaced files and the database snapshot, then a restart of the old app. Backups, rollback manifest and result metadata remain under the selected data folder's `updates` directory. This protocol has not been exercised in this turn. Tool updates verify file integrity only; use an explicit connector check and functional review afterward. No automatic tool-health rollback is claimed.

Remote release discovery, signature verification/download installation, arbitrary source-build recipes, a manual rollback browser, generic GUI automation and test-verified local coding qualification remain outside this implementation. Existing smart testing continues to require approved commands and is not invoked by this edit.

## Data and verification boundary

SQLite additions are additive tables and optional JSON fields; source implementation does not touch the user's current database. No external tool source, credentials, account settings or running processes were changed. The source sync retains a backup of replaced files and refuses concurrent source drift. Build/test results for these changes are intentionally unavailable because the user requested no build/tests.
