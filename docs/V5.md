# V5 — AI/tool orchestration with focused skills

Implemented in source, 2026-11-02. No application build, runtime tests, model inference or tool generation was performed for this change. This extends the V3/V4 connectors; it does not claim new unsupported backend features.

## User flow

1. In Settings > Tools, enable/configure the existing tool, its workspace/API and required write/model permissions. Start the tool's backend where required, then use Check connection. For unattended internal steps also enable **Cho phép Tasks tự sử dụng tool (không tự đăng bài)** and save the profile. This permission defaults off.
2. Leave **V5: AI chọn skill và điều phối công cụ trong Tasks** enabled. Use Automatic for policy-approved continuation, and enable continuing internal steps in task defaults. SemiAutomatic/Manual retain plan, action and result approval gates. Final parent-task review remains required in every mode.
3. In Tasks choose the real game project and approved WriteProject if integration/code edits are requested. Enter, for example: “Thêm nhân vật mèo đi lại. Dùng Pixel Art Tool tạo sprite và animation, giữ phong cách game rồi tích hợp vào project.” No saved workflow or workflow JSON is required.
4. Run/resume. The coordinator can produce AI inspection/input preparation → Pixel create → input preparation → Pixel animation → AI integration. Steps and Plan show executor and selected skill. Review requests/results through the task's decisions, or in Tools; Resume recognizes externally approved/reviewed requests.
5. Inspect the final result/changed files and approve parent completion. A tool invocation succeeding does not certify art quality, animation quality or tests.

Video example: “Kiểm tra project TrailerForge đã lưu trong [actual allowed folder], xuất trailer rồi chuẩn bị media marketing.” The video connector only inspects/exports saved projects. It cannot make a film from text without a supported backend operation. Marketing publishing still needs per-request explicit approval and backend account/review prerequisites.

## Planning and runtime

- Ordinary simple tasks retain deterministic orchestration. Tool/media keywords and configured tool names trigger mixed planning. Feature creation requests can also trigger semantic planning when a supported tool is enabled, so the coordinator can decide whether tools are useful even without a media noun. Existing complex-task planners receive the tool metadata catalog too. A plan may correctly choose only AI steps if no tool is useful.
- The coordinator receives compact capability metadata, enabled/permission state and exact tool/operation IDs. It does not receive every skill body. It cannot enable connectors, add unimplemented operations or exceed project/access grants.
- A planned task may carry skillId and a ToolTaskSpec (toolId, skillId, operation, exactly one of input or inputFrom). InputFrom is an explicit AI preparation dependency. Preparation receives its target skill automatically, reads only within approved scope, returns {toolInput:{...}} and does not edit the project or call external tools itself.
- C# validates operations, permissions, graph, project membership, input-source dependency, skill identities and bounds before plan acceptance. Approved steps persist plan keys, selected skill/hash, tool specs and run IDs in the existing task JSON. No schema renumbering or replacement of user data is needed.
- SessionEngine dispatches tool steps separately from AI steps. Automatic execution/review applies only under the explicit tool task-automation policy, Automatic mode, existing operation permissions and internal continuation policy. Publishing never uses this automatic approval path.
- Exact-input approvals and profile hashes remain checked by ToolExecutionService. Changing a bound step/project root or changing a selected skill invalidates its old binding; it cannot silently replay a write. Completed requests are reused. Failed/interrupted writes stay recorded and require inspection/a fresh request rather than blind replay. A temporary project/tool resource conflict pauses a still-unexecuted request for explicit resume.
- Tool roots are reserved under the owning task slot, while excluding overlapping work from other tasks. The connector's single-request gate remains authoritative. Tool calls reserve global usage and the session call budget before model-using operations. This counts manager reservations, not exact vendor/internal tool calls or currency.

## Skills and extension

Authoritative project skills:

- `.agents/skills/employee-pixel-art/SKILL.md`: create/edit/animation API guidance, source image handling, sheet layout and integration checks.
- `.agents/skills/employee-video/SKILL.md`: saved-project inspection/export, workspace and rendering limits.
- `.agents/skills/employee-marketing/SKILL.md`: project/media/job IDs, drafts, backend review and publishing boundaries.

Each folder also has a small `tool-skill.json` descriptor (Id, Description, Connector, Operations, Keywords). The app reads metadata at startup and body text only for selected execution/preparation steps. A custom skill must target an already implemented connector/operation; adding SKILL.md cannot manufacture an API, run arbitrary scripts or automate an unknown desktop application. No scripts are automatically executed by this registry. Restart the app after editing descriptors. Project skills are packaged as application content under skills/ on a manual build; no global skill copy/configuration was changed.

Settings lists the loaded catalog/status. Model/provider routing still uses the existing measured history and budgets; a tool skill is guidance, not a new model, model training or a guarantee of lower vendor billing.

## Media and context savings

- Skill bodies are bounded and lazy-loaded; dependency results are bounded, labelled as untrusted data and included only for declared dependencies. API call execution, polling, graph traversal, references and checkpointing are deterministic C#.
- {$from: "key.field"} reuses a completed declared dependency field. {$imageFrom: "key"} loads that dependency's managed PNG with hash verification. {$projectPng: "Assets/file.png"} reads only a PNG within the selected project under approved ReadProject scope, refusing redirected paths. {$attachmentPng: "file.png"} reads the user's original attached PNG. The app converts bytes to data URLs; AI is never asked to output base64.
- Pixel output includes managed artifact path/SHA256, actual PNG header dimensions, request frame/timing metadata and backend sheet columns/rows. Generated art may still need visual review and engine-specific import/slicing/scaling by the integration worker. The connector does not claim the frontend's unrelated postprocessing steps were run.
- Marketing media imports are limited to the selected project, the configured allowed tool workspace or declared completed tool artifacts. No credentials are loaded into skill prompts.
- Suitable existing assets/results should be reused; generation/refinement should follow a concrete requirement or defect. Planning/preparation can still consume AI calls; no blanket percentage saving is claimed. Pixel Art Tool uses its own Codex session and can hit its own usage limit.

## Verification and known limits

Source review covers dispatch, pending decisions, resume/reuse paths, budget reservations, permissions, packaging and markup structure. No application compilation or runtime validation was requested/performed. The three bundled skill-validator attempts could not start because the installed Python lacks PyYAML (`ModuleNotFoundError: yaml`). No dependency was installed solely to run validation. Skill frontmatter, metadata and linked operations were inspected directly; this does not substitute for runtime behavior checks.

Existing explicit saved workflows remain supported. This feature does not add autonomous skill rewriting, automatic backend/software installation, browser clicking, new image/video services, free usage or unrestricted publishing. No release build or ZIP was generated.
